# PR Critical Review

PR の懸念を列挙して終わるのではなく、人間が確認すべき範囲を絞り、残りを「なぜ見なくてよいか」まで含めて説明する。

次の原則を守る。

1. 調査範囲と終了条件を先に決める。
2. 根拠のない安心を出さない。
3. 高度な指摘ほど、利用者に起きる影響を平易に説明する。
4. 既存コメントで決着済みの論点を再提起しない。

## 対象と入力

入力は `$ARGUMENTS` とする。

```text
{PR番号} [保存先] [--out path] [--profile-only] [--tone ja|en]
```

- PR 番号は `123` と `#123` の両方を受け付ける。
- 位置引数の保存先と `--out` は同義。両方あれば `--out` を優先する。
- 保存先が `.md` で終わればファイル名、それ以外はディレクトリとして扱う。
- `--profile-only` はリポジトリプロファイルを表示して終了し、ファイルを書かない。
- `--tone` がなければ PR 本文と既存コメントの主言語に合わせる。
- 未知のフラグ、PR 番号の欠落、矛盾した入力があれば、推測せず使い方を示して停止する。

この skill は Markdown 専用である。図解を求められた場合だけ [references/deferred-features.md](references/deferred-features.md) を読み、未実装であることと再導入に必要な作業を説明する。通常のレビューではこの reference を読まない。

## 安全性と権限

レビューは読み取り専用で行う。PR、Issue、ブランチ、外部環境を変更しない。

### 許可する操作

- `gh pr view`、`gh pr diff`、`gh pr checks`、`gh pr list`
- `gh issue view`、`gh repo view`
- GET に限定した `gh api`。曖昧さを避けるため `--method GET` を明示する
- `git status`、`git show`、`git diff`、`git log`、`git merge-base`、`git rev-parse`、`git ls-files`、`git remote get-url`
- リポジトリと取得済みメタデータに対する `rg`、`find`、`sed`、`sort`、`wc` などの読み取り
- 決定した出力先へのレビュー Markdown の保存

### 禁止する操作

- `gh pr create/edit/close/merge/comment/review/reopen/ready` などの書き込み
- POST、PATCH、PUT、DELETE を行う `gh api`
- `git fetch`、checkout、pull、commit、push など、作業ツリーや Git メタデータを変える操作
- CI や設定から見つけたテスト、lint、build、deploy コマンドの実行
- クラウド、データベース、外部サービスを照会または変更する CLI の実行
- パッケージのインストール
- `.gitignore`、設定ファイル、レビュー対象コードの変更

外部環境の実値がなければ決着しない懸念は、勝手に照会せず「未確認」にする。確認主体、対象、必要なコマンドまたは画面、期待する判定を具体的に書く。読み取りに見えるコマンドでも課金やロックを伴い得るため、接頭辞だけで安全と判断しない。

## 成果物と出力先

成果物はレビュー Markdown 1 ファイルだけとする。

出力先は次の優先順で一度だけ決める。

1. `--out` または位置引数の保存先
2. `.pr-review.json` の `outputDir`
3. `${XDG_STATE_HOME:-$HOME/.local/state}/pr-review/{owner}__{repo}/pr-{番号}-critical.md`

明示指定なしでレビュー対象リポジトリ内へ書かない。親ディレクトリは必要な場合だけ作成する。書き込みに失敗した場合は無断で別の場所へ保存せず、失敗理由と予定していた絶対パスを返す。

`--profile-only` 以外の正常終了時は、標準出力に PR、トリアージ件数、PR 作成者への質問、成果物の絶対パスを短く表示する。

## Workflow

### 1. 前提条件を確認する

次を確認し、必須項目を満たさなければレビューを開始しない。

- 現在地が Git リポジトリである。
- `gh` と `git` が利用できる。
- `gh auth status` が成功する。
- 指定 PR のメタデータと差分を読み取れる。

メタデータまたは差分を取得できなければ、レビュー結果を推測で作らず停止する。既存コメントや CI など補助情報だけが取得できない場合は処理を続けてもよいが、取得失敗を「未確認」と探索範囲へ記録する。

### 2. リポジトリプロファイルを作る

案件固有の規約や構成を skill 本文から推測しない。最初に次の順で設定を探す。

1. リポジトリ直下の `.pr-review.json`
2. `.claude/pr-review.local.json`
3. 未指定項目だけ自動発見

設定では次を受け付ける。

- `conventions`: 明文規約のファイル
- `specSources`: 仕様の探索先
- `packages`: パッケージ一覧
- `environments`: 環境名の集合
- `validateCommands`: CI が実行する検証コマンド。発見情報としてのみ使い、実行しない
- `outputDir`: 既定出力先
- `tone`: `ja-keigo` または `en-neutral`
- `extraCriticalChecks`: `when`、`check`、`why` を持つ案件固有観点。`why` がない項目は採用しない

自動発見では、存在するものだけを読む。

- 適用対象の `AGENTS.md`、`CLAUDE.md`、`CONTRIBUTING*`、`STYLEGUIDE*`、`ARCHITECTURE*`、`.github/instructions/**`、`.cursor/rules/**`、`docs/adr/**`、`docs/decisions/**`
- 言語、lockfile、workspace 定義、manifest から得られるパッケージ構成
- CI workflow、task runner、manifest scripts に定義された自動チェック
- OpenAPI、GraphQL、Protocol Buffers などの API 契約
- DB スキーマ、migration、ORM 設定
- IaC と環境別設定
- PR テンプレートと、課題番号を含むリポジトリ内文書

規約は変更ファイルに最も近いものを優先し、合計 2,000 行を上限にする。超える場合は見出しと、差分から得たキーワードに対応する節だけを読む。git 管理外のローカル規約も、現在のファイルシステム上に存在すれば対象にする。

見つからなかったものを一般論で補わない。

- 明文規約がない: 微修正を無効化し、探索した場所を記録する。
- 自動チェックが分からない: format、命名、spell、未使用コードの指摘を出さない。
- API 契約がない: 要件照合を PR 本文、Issue、コード内契約に限定する。
- 環境集合が分からない: 環境追随漏れを網羅確認済みと主張しない。
- 課題ミラーがない: 経緯探索を GitHub と git 履歴に限定する。

レビュー冒頭に次を 5 行以内で提示する。

```text
検出: {単一パッケージ、または全Nパッケージ} / 規約 {N} 本 / API契約 {N} 本 / 環境 {一覧またはN/A}
委譲: {CIやlintへ委譲する観点、またはN/A}
検証: {CI定義から確認したコマンド。実行はしていない}
仕様: {仕様・課題の探索元、またはN/A}
未適用: {発見できず落とした観点}
```

`--profile-only` ならここで表示して終了する。

### 3. PR と既存の議論を取得する

最低限、次を取得する。

- number、title、body、author、base/head branch、head commit OID、state、additions、deletions、changed files
- 差分と変更ファイル一覧
- `gh pr checks` の結果
- review comment、review thread、通常の Issue comment
- PR の commit message

差分が概ね 1,000 行を超える場合は、先に変更ファイル一覧と変更種別を把握してから、契約、永続化、境界、設定、テストの順に調査を組み立てる。大きいことを理由にファイルを黙って除外せず、未調査範囲が残れば列挙する。

既存コメントは、現在の head のコードと突き合わせて次に分ける。

- 対応済み: 実装への反映を確認し、同じ指摘を出さない。
- 見送り・合意済み: 同じ判断を再提起しない。
- 未対応・部分対応: 残っている部分だけを扱い、既存指摘との差を示す。
- 事実誤認: コードや一次資料の所在を示して補正する。

変更後コードの行番号は、まず手元に同じ head OID の ref があるか確認する。なければ GET の `gh api` で head OID のファイル内容を取得する。どちらも使えず diff hunk から推定した場合は、推定値であることを明記する。実在を確認できない `path:line` を断定しない。

### 4. 経緯カードを埋める

次の4問へ、出典付きで答える。

1. この PR は何を達成するか。
2. なぜ今必要か。
3. 採用しなかった案と理由は何か。
4. この領域で既に決まっている方針や前例は何か。

Issue、PR、commit を出典にするときは、番号や hash だけでなく内容を1文で要約する。

安い探索から進め、4問が埋まった時点で終了する。

1. PR 本文、ブランチ名、commit message、PR テンプレート
2. リポジトリ内の仕様、課題ミラー、コードコメント
3. linked Issue
4. 変更ファイルの履歴から見つかる関連 PR と同領域の merged PR

探索上限は次の通り。

- 経緯の検索・取得は通算12コマンドまで
- 新規に開く文書は8本まで、各400行まで
- 過去 PR は5本まで、本文だけ
- Slack、メール、会議、人への問い合わせは探索対象外

未回答が残ったら、探索範囲を示し、複数の不足を可能な限り1つの具体的な質問へまとめる。経緯が確認できない領域について「要件違反」や「仕様との不一致」を断定しない。コードだけで完結する例外、データ破壊、認証欠落などは通常通り評価する。

### 5. 疑いを立てる

差分の各変更について「問題である」と決めつけず、まず疑いとして内部表へ記録する。

```text
ID | 疑ったこと | 判定 | 深刻度 | 根拠強度 | 根拠の所在 | 決着方法
```

最低限、該当する次の観点を確認する。

- 削除・更新・検索条件のスコープ
- null、空、0件、失敗、再試行、並行実行の分岐
- 変更された関数、型、契約の全呼び出し元
- API、DB、イベント、ファイル形式との契約
- 一意制約、外部キー、cascade、transaction、cache の整合性
- 認証、認可、秘密情報、公開範囲
- 登録表、routing、export、環境別設定など二重管理の片側漏れ
- schema と利用コード、複数サービスなどのリリース順序
- 全パッケージ、全環境、共有データへの波及
- テスト、監視、alert、rollback という安全網
- `.pr-review.json` の `extraCriticalChecks`

シグネチャや登録対象を変更した場合は、固定文字列検索など再現可能な方法で参照を全走査する。全数確認を名乗るなら検索式、除外条件、発見総数 N、N件すべての結論を残す。

### 6. 根拠を評価してトリアージする

根拠は次の5段階だけを使う。

| 強度 | 根拠 | 条件 | 「見なくてよい」に使用 |
| --- | --- | --- | --- |
| R1 | 実行済み証跡 | CI の成功結果と、その検査が実行される定義の両方を示せる | 可 |
| R2 | 全数確認 | 検索方法と発見総数 N を示し、N件をすべて確認した | 可 |
| R3 | 一次資料 | 仕様、契約、明文規約の該当箇所を示せる | 可 |
| R4 | 構造上の不変 | 結論を直接確認できる変更後コードの `path:line` を示せる | 可 |
| R5 | 推論のみ | 読んだ印象以上の所在を示せない | 不可 |

R1 は job 名が success というだけでは成立しない。CI 定義から今回の懸念を検査する処理へ結び付ける。テストファイルが存在するだけでも R1 にしない。

R4 は「その不変を変更後コードのどこで確認できるか」で判定する。所在を示せなければ R5 とする。迷う場合も R5 に倒す。

疑いの判定は次の3値とする。

- `閉`: R1〜R4 があり、確認結果から追加判断も対応も不要と言える。
- `指摘`: 問題への対応または人間の許容判断が必要。
- `未確認`: R5、情報不足、権限不足、取得失敗などで決着していない。

根拠が強くても次は `閉` にしない。

- 変更を守るテスト、監視、alert、rollback がない。
- 停止、通信断、性能劣化が発生する。
- 権限や公開範囲が広がる。
- data migration、破壊的 schema 変更など取り消しにくい。
- 継続的な費用が増える。

これらは事実の有無と、その状態を許容する判断を分け、後者を人間へ渡す。

`未確認` は全件出す。`閉` だけは件数と根拠別内訳を明示した上で代表例へ圧縮してよい。次の式が一致することを確認する。

```text
疑い総数 = 指摘 + 未確認 + 閉
```

### 7. 指摘の深刻度を決める

`指摘` は次に分類し、深刻な順に並べる。

- `Critical`: 明確な要件未達、例外・無限処理、データ破損や喪失、認証認可の欠落、秘密漏洩、整合性破壊、実行時だけ判明する結線漏れ、破壊的インフラ変更など、マージを止める理由がある。
- `要検討`: 事実は確認できたが、運用、互換性、停止、安全網、費用などの許容判断が必要。
- `参考`: 対応必須ではないが、根拠のあるリスク情報として残す価値がある。
- `微修正`: Critical と要検討がともに0件の場合だけ、明文規約への違反を最大3件。

「検知できないから Critical」とする前に、別の通知、下流障害、定期的な突合、監視がないか確認する。実在する検知経路があれば、その実効性を人間が判断する `要検討` にする。探索してもなければ、探索範囲を添えて Critical とする。

微修正は規約の `path:line` と短い引用を必須とする。既存のベース側コードが同じ形なら、新しい違反でない限り取り下げる。format、import順、spell、未使用変数など CI や lint に委譲された観点は出さない。件数合わせをしない。

### 8. 読み手向けに翻訳する

各指摘には、実装用語を使わず利用者や運用へ何が起きるかを30〜60字で先に書く。それだけで意味が通らなければ、指摘としての理解が不足しているので未確認へ戻す。

クラウド/IaC の合成、runtime 内部、SQL の三値論理、分散反映、特殊値を使う型設計などの説明には、指摘本文より前に2〜4行の前提を置く。前提を平易に説明できない場合も未確認へ戻す。

固有名詞は初出で役割を説明し、IssueやPRは番号だけで参照せず、数値には単位と対象を付ける。PR 本文はそのまま写さず、経緯を知らない新規参加者にも分かる形へ言い換える。

### 9. Markdown を生成する

目安は4,000字以内。ただし人間判断と未確認の全件、母数、根拠の正確さを字数より優先する。長くなる場合は `閉` の詳細だけを圧縮する。

Critical が0件なら、ヘッダ直後にその事実を明記してから要検討や参考を続ける。

```markdown
# PR #{番号} クリティカルレビュー: {タイトル}

> プロファイル: {5行以内の検出結果}

| 項目 | 値 |
| --- | --- |
| 作成者 | {author} |
| ブランチ | {head} → {base} |
| トリアージ | 疑い {N} / 指摘 {M} / 未確認 {J} / 閉 {K} |

## {クリティカル指摘 N 件 / クリティカルな指摘はありません}

### C1: {利用者への影響を表す一文}

> `{path}:{line}`

{必要なら技術的前提}

{問題 → 影響 → 根拠の順に簡潔に説明}

**判断または対応してほしいこと**: {具体的な選択肢または修正結果}

## 人間の判断が必要な点

### D1: {一文}

{確認済みの事実と、人間に残る判断を分けて記載}

## 未確認

- U1: {疑い} → 決着には {誰が、何を、どう確認するか}

## 確認の結果、追加レビューが不要な点

根拠別内訳: R1 {N} / R2 {N} / R3 {N} / R4 {N}

- {影響が大きい代表例}: {疑い → 確認方法 → 結論。根拠の所在}

## 経緯として確認した範囲

- Q1〜Q4 の回答と出典
- 探索した文書、Issue、過去PRの件数
- {残った場合だけ} PR作成者への質問: {1問}

## 微修正

- {Criticalと要検討が0件で、明文規約がある場合だけ}
```

日本語では敬体を使い、問題、影響、依頼を直接かつ穏やかに書く。英語では簡潔で中立的な提案調にする。個人名や役職による評価は書かない。

### 10. 保存前に整合性を検査する

次を満たさない場合は保存前に修正する。

- トリアージ件数の合計が疑い総数と一致する。
- Critical、要検討、未確認が省略されていない。
- `閉` の全項目が R1〜R4 と検証可能な所在を持つ。
- R1 が実行結果と CI 定義の両方を持つ。
- R2 が検索式、除外条件、総数を持つ。
- R4 の `path:line` が変更後コードを指す。
- 既存コメントで決着済みの指摘を重複させていない。
- 経緯不明なのに要件違反を断定していない。
- PR へ投稿する命令や、実行していないテストの成功主張がない。
- 成果物以外のファイルを変更していない。

保存後、成果物の絶対パスと短いトリアージ要約を返す。PR への投稿は、ユーザーが明示的に別途依頼しても、この skill の実行内では行わない。
