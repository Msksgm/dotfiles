# review-io-impact

変更差分を起点に、**処理全体の input（入口）→ output（出口）への影響**を辿り、**単体テスト・シナリオ/e2e テストのカバレッジ**を確認し、それを**読み手が理解できる説明に翻訳する**ためのレビュー補助 skill。

この skill が担うのは次の3点:

1. 変更が「どの入口（リクエスト/バッチ引数）」から入り「どの出口（永続化/ファイル・CSV/レスポンス/イベント）」に、どんな条件で影響するかのトレース
2. その経路が単体テスト・シナリオ/e2e テストでカバーされているかの突合とギャップ指摘
3. **その結果を、レビュアーが自力で判断できる説明に翻訳する**（入口カタログ / before→after / 因果連鎖 / ドメイン語 / 図）

**対象外**: バグ検出・ロジック誤り・ルール準拠・セキュリティ・スタイル。これらは各プロジェクトのレビュー手段に委ねる。重複して指摘しない。

**入力情報**: $ARGUMENTS

## モード

トリガー語と引数からモードを判定し、実行する Step を決める。

| モード | 起動条件 | 実行する Step |
|---|---|---|
| `impact`（既定） | 「影響トレース」「カバレッジ確認」等 | Step 0〜6 |
| `explain` | 「解説して」「どのオペレーションが呼ばれる」「経路を図で」等 / `--explain` | Step 0〜6 ＋ **Step 7〜11** |
| `explore` | 差分が無い・引数が機能名/ファイル（既存機能の理解） | Step 0〜5 ＋ Step 7〜11（**Step 9 の before/after は省略**。Step 6 は「既存テストの所在」だけ示す） |

判定結果はレポート冒頭に明記する（プロジェクト map の使用/未使用と並べて）。

## Step 0: プロジェクト適応（project adapter）

この skill は stack 非依存で自己完結するが、リポジトリが**固有の surface map** を提供していれば、その具体シグナル/grep を優先して精度を上げる。

1. 規約パス `.claude/review-io-impact/io-surface-map.md` の存在を確認する。

   ```bash
   test -f .claude/review-io-impact/io-surface-map.md && echo FOUND || echo NONE
   ```

2. **FOUND** の場合: そのファイルを Read で読み込み、以降の Step 2/3/4/6/7/11 では **map に書かれた層判定表・grep・テスト方針・用語集を優先**する（本 skill の汎用シグナルは補助）。
3. **NONE** の場合: 本 skill 内蔵の**汎用シグナル**（下記「汎用シグナル」）で surface を導出する。

出力レポート冒頭に「**プロジェクト map: 使用 / 未使用**」を必ず明記する。

> map は次の任意セクションを持てる（あれば優先参照、無くても動作は変わらない）:
> **用語集** — ドメイン語とコード上の実体（クラス/フィールド/テーブル）の対応表。Step 11 の抽出元として最優先で使う。

## 汎用シグナル（language/stack 非依存）

プロジェクト map が無いときのフォールバック。変更箇所の役割を、パス・命名・呼び出し形から次の類型に当てはめて判定する。

### input（入口）の類型
- **HTTP / RPC ハンドラ**: ルーティング登録、コントローラ/リゾルバ、`handler`/`controller`/`resolver`/`endpoint` 命名、フレームワークの受信アノテーション
- **CLI / entrypoint**: `main`、`command`/`cmd`/`entrypoint` 配下、引数パース
- **キュー / ジョブ consumer**: `job`/`worker`/`consumer`/`subscriber`、メッセージ/パラメータの受け口
- **cron / スケジュール**: 定期実行の登録・ハンドラ

→ 「リクエスト/引数を**最初に受ける関数**」を特定し、その入力の形（フィールド・パラメータ名）を記録する。

### output（出口）の類型
- **DB 書込・マイグレーション**: repository の `save`/`insert`/`update`/`upsert`/`delete`、ORM のテーブル定義、DDL
- **ファイル / CSV 出力**: ファイル書き出し、CSV/帳票ビルダ、ストレージアップロード
- **外部 API / RPC 呼び出し**: クライアント/スタブ経由の送信
- **イベント発行**: publish/emit、outbox
- **キャッシュ書込**: cache set/put

### 調整層
- usecase / service / interactor / handler があれば、そこを input→output の**結節点**として上下に辿る

### テスト
- プロダクションと**ミラー配置の単体テスト**ディレクトリ（`test`/`tests`/`__tests__`/`*_test.*`/`*Test.*`/`*.spec.*`）
- e2e / シナリオ / 受け入れテストのディレクトリ（`e2e`/`scenario`/`integration`/`acceptance`）

## Step 1: 変更差分の取得と分類

引数（`$ARGUMENTS`）を解釈して変更ファイル一覧と差分を取得する。

- **数字のみ** → PR 番号。`gh pr diff <n>` と `gh pr view <n> --json files -q '.files[].path'`
- **パスらしき文字列** → そのファイル/ディレクトリを対象
- **空** → 既定ブランチとの差分。既定ブランチは `git rev-parse --abbrev-ref origin/HEAD`（取れなければ `main`/`master`/`develop` を順に確認）を基準に `git diff --name-only <base>...HEAD` と `git diff <base>...HEAD`
- **差分が取れない / 引数が機能名** → `explore` モードに切り替え、その機能の実装起点を特定して Step 2 へ

取得したファイルを分類する:
- **プロダクション**（実装コード）
- **単体テスト**
- **シナリオ / e2e**
- **その他**（スキーマ、proto、設定、ドキュメント等）

> テスト・シナリオのみの差分なら、カバレッジ判定ではなく「テスト自体が変更対象の振る舞いを正しく検証しているか」に観点を切り替える。

---

## Step 2: 変更箇所の層を特定

各プロダクション変更ファイルについて、それが input 寄り / 調整層 / output 寄りのどこかを判定する。

- プロジェクト map があれば、その**層判定表**（パスシグナル → 層 → 上流 grep / 下流 grep）に従う
- 無ければ「汎用シグナル」の類型で判定する

判定できたら、各ファイルについて「上流（input 方向）に辿る手掛かり」「下流（output 方向）に辿る手掛かり」をメモする。

---

## Step 3: input（入口）まで遡上

変更箇所から、それを呼ぶコード（呼び出し元）を逆引きして**入口**まで遡る。

- 変更した関数/クラス名で呼び出し元を検索（`grep -rn "<Name>" --include=<ext>`）し、調整層 → 入口ハンドラへと辿る
- 入口に到達したら記録する:
  - **入口の種類**（HTTP/RPC エンドポイント名、CLI コマンド、ジョブ名、cron）
  - **入力の形**（リクエスト/引数のフィールド、バッチパラメータ）
- 複数の入口から到達し得る場合は**すべて**列挙する（変更の波及範囲になる）

---

## Step 4: output（出口）まで追跡

変更箇所から辿れる**副作用**をすべて列挙する。

- **永続化**: どの repository → どのテーブル/コレクションへ、何を書くか
- **ファイル / CSV / 帳票**: どの出力物のどの箇所に効くか
- **レスポンス / イベント**: 返却値・発行イベントのどのフィールドが変わるか
- **外部呼び出し**: 別サービス/API への送信内容

RPC/サービス跨ぎがある場合は、クライアント → 相手サービスのハンドラ → その usecase へ**二段以上**で辿る（プロジェクト map の「跨ぎ境界」節があれば従う）。

---

## Step 5: 影響マップの作成

Step 3・4 を統合し、経路を可視化する。

```
input（エンドポイント / パラメータ）
   → [変更箇所（層・関数）]
   → output（永続化テーブル / 出力ファイル / レスポンス・イベントのフィールド）
```

- 分岐がある場合は分岐ごとに経路を分ける
- 各 output について「**変更がどの output を、どういう条件で変えるか**」を1〜2行で言語化する（例: 特定の分岐条件のときだけ、この出力カラムの丸め方が変わる 等）

---

## Step 6: テストカバレッジ確認

Step 5 で洗い出した経路が、テストで守られているかを突合する。

### 単体テスト
- 変更した各プロダクションクラス/関数に対応する**ミラーテスト**を検索する
  - プロジェクト map があれば、その具体パス規約・実行コマンド例に従う
  - 無ければ汎用: `find <test-root> -name "<Class>*<TestSuffix>"` ＋ `grep -rl "<Class>\|<function>" <test-root>`
- 見つかったテストが、変更した**分岐・条件**を実際に通しているかを確認する（存在するだけでなく、当該経路を検証しているか）

### シナリオ / e2e
- 入口が判明していれば、そのエンドポイント名・ジョブ名でシナリオを検索
- ドメイン観点（機能名・キーワード）でもシナリオを検索
- 期待値ファイル（スナップショット/expected）に当該出力が含まれるか

### 既存 / 新規の区別
- 差分に含まれるテスト = **本変更で追加/修正されたテスト**
- 差分に含まれないが当該経路を通るテスト = **既存テスト**

この2つは**必ず分けて記録する**。「テストがある」だけでは、その変更のために書かれたのか元からあったのかが読み手に伝わらない。

### 方針判定（単体 vs シナリオ）
- プロジェクト map に「単体 vs シナリオ/e2e の使い分け」があれば**それを適用**する
- 無ければ汎用則: **純粋ロジック（計算・変換・判定）は単体**、**複数コンポーネント/永続化/期間・状態を跨ぐフローはシナリオ/e2e** で守る

### ギャップ判定
経路ごとに (a) 単体の有無 (b) シナリオ/e2e の有無 を突合し、次を明示する:
- **単体だけ** / **シナリオだけ** / **両方あり** / **両方欠落**
- 方針上「本来どちらが必要か」と、実在との差分（＝追加すべきテスト）

## Step 7: 入口カタログをプロトコル別に整理

Step 3 で集めた入口を、**プロトコル種別ごとの表**に組み直す。1つの表に混ぜない。読み手は「自分が触っている層の入口」だけを見たいため。

- 種別の例: GraphQL Operation（Query/Mutation/Subscription）/ gRPC メソッド（`Service/Method`）/ REST ルート（`METHOD /path`）/ CLI コマンド / job・worker / cron / イベント consumer
- 各行に **operation 名・入力の形・変更箇所までの到達経路**を書く
- **「影響しない近縁の入口」も別枠で明記する** — 同じ調整層を呼ぶが変更箇所まで降りないものを挙げると、レビュアーの確認範囲が確定する。これは省略しない
- 入口が**同一プロセス内呼び出しか、ネットワーク越し（RPC）か**を区別する。「リゾルバが RPC を挟むのか、UseCase を直接呼ぶのか」は誤解が生まれやすいので、確認して事実を書く
- 「入口 A → ジョブ enqueue → 別プロセスで実行」のように非同期を挟む場合、その境界を明示する

---

## Step 8: 合流点（choke point）の特定

複数の入口が 1 点に収束するなら、それを明示する。

- **収束する場合**: 「入口が何であれ必ずここを通る」→ 影響範囲はその点に到達する経路と等価、と言い切る。これが言えると読み手の確認コストが大きく下がる
- **収束しない場合**: 分岐したまま列挙し、経路ごとに影響を分ける。無理に1点にまとめない

---

## Step 9: before→after の対比（`explore` モードでは省略）

変更した関数について、**シグネチャの変化**と**意味の変化**を分けて擬似コードで並置する。

```
Before:  X = f(a, b)        ← a は null になり得る前提が無く例外
After:   X = g(c)           ← c は呼び出し元で組み立て、値の出どころも変わる
```

- 「**null 安全化だけなのか**」「**値の意味（算出根拠・単位・累計範囲）も変わるのか**」を必ず切り分けて書く。後者なら既存正常系にも回帰リスクがあり、レビュアーが見るべき箇所が変わる
- 引数が増減した場合、**デフォルト引数で誤魔化していないか**（＝全呼び出し元が更新されているか）を確認して事実として書く
- 型が変わった場合、nullable/non-null・コレクション/単数・数値の精度が変わっていないか確認する

---

## Step 10: 因果連鎖の言語化

「なぜ今の実装が問題なのか / この変更で何がどう変わるのか」を**矢印 1 本の連鎖**で書く。条件 → 中間状態 → 症状、の粒度で刻む。

```
<入力条件> → <中間データが欠落/変化> → <判定が通らない> → <観測される症状>
```

- 各ステップは検証済みの事実に限る。推測が混ざるなら「ここは未確認」と明記する
- 症状は**観測可能な形**（例外で落ちる / 値がズレる / データが保存されない）で書く。「バグる」では読み手が確認できない

---

## Step 11: ドメイン語とコード上の実体の対応付け

差分・経路説明に登場する**非自明なドメイン語を抽出**し、読み手が知らない前提で解説する。

- 抽出元の優先順:
  1. プロジェクト map の**用語集**セクション（あれば）
  2. コード内の KDoc/docstring・日本語識別子・enum 値
  3. 変更差分のコメント
- 解説には**コード上の実体**（どのクラス/フィールド/テーブルが対応するか）を必ず添える。辞書的定義だけで終えない
- 用語が**階層・順序を持つ概念**なら、その順序が計算・処理にどう効くかまで書く
- 説明の中で新しい非自明な語を使ってしまったら、それも解説対象に加える（再帰的に潰す）

## 図の記法ルール

| 出力先 | 記法 | 理由 |
|---|---|---|
| 会話（既定） | **ASCII 罫線** | ターミナルでそのまま読める |
| crit / GitHub / Notion 等のレンダラ | **Mermaid** | crit は Mermaid を同梱しており描画できる |

**既定は ASCII**。Mermaid は貼付先が明示されたときだけ使う（crit 出力は「明示された」ケースに当たる。§crit でブラウザ表示する 参照）。

描く図は最大 3 枚:

1. **全体図** — 入口群 → 合流点 → 変更箇所 → 出口群。合流点を視覚的に強調する
2. **入口別図** — プロトコルごとに、operation から変更箇所までの到達経路
3. **出口図** — 変更箇所から永続化・ファイル・レスポンス・イベントへの波及

図を増やしすぎない。3 枚を超えるなら表に落とす。

## crit でブラウザ表示する

レポートをブラウザで読みたいときは `crit` に渡す。全モードで有効。

### 発火条件

ユーザーが「crit で見たい」「ブラウザで」「html で」等と言ったとき、または引数に `--crit` があるとき**だけ**実行する。**既定では会話に出すだけでファイルは書かない。**

### 手順

1. 会話に出したレポート本文と**同一の内容**を Write で書き出す。
   - 出力先: `${TMPDIR:-/tmp}/review-io-impact-<slug>.md`
   - `<slug>` は対象（PR 番号 / ブランチ名 / 機能名）から作る
   - **リポジトリ内には書かない**。レビュー成果物を git に混入させないため
2. 図は Mermaid で書き直す（crit が描画できるため。§図の記法ルール 参照）
3. `crit <絶対パス>` を **`run_in_background: true` で起動する**
   - crit は「Finish Review」がクリックされるまでブロックするため、**フォアグラウンドで実行してはいけない**（会話が止まる）
4. 起動ログの `Started crit daemon at http://localhost:<port>` を拾い、URL をユーザーに報告する
5. ユーザーがブラウザ上でコメントを残したら `crit comments --json` で回収して対応する（コメント操作の詳細は crit プラグインの `crit-cli` skill の領分）

### 注意

- crit は**レビュー UI** であり、行番号ガーターとコメント欄が常に付く。読み取り専用の閲覧モードは無い
- **静的 HTML ファイルは生成されない**。crit はローカルサーバを立ててクライアント側で描画する（`crit export` や `--html` は存在しない）。オフラインで配れる成果物が要る場合は `crit share` を使うが、これは外部サービス（`crit.md`）への**アップロード＝ネットワーク送信**を伴うので、**ユーザーの明示指示なしに実行しない**
- `open ~/.crit/sessions/<id>.lock: operation not permitted` (EPERM) で起動に失敗する場合は、`~/.crit` がサンドボックスの書き込み allowlist に入っているか確認する

## 原則

- **断定と推測を分ける** — 確認したことは `path:line` を添えて断定し、確認していないことは「確認ポイント」として渡す。読み手の判断を奪わない
- **用語を放置しない** — 説明中に非自明な語が出たらその場で定義する
- **影響しないものも書く** — 「これは影響しない」は安心材料であり、レビュー範囲の確定に効く
- **図と表を先に、散文を後に** — 構造を掴んでから詳細を読めるようにする

`explain` / `explore` モードでは加えて:

- [ ] 入口をプロトコル別に分けて列挙したか
- [ ] 「影響しない近縁の入口」を明記したか
- [ ] 同一プロセス呼び出しと RPC 越しを区別したか
- [ ] 合流点の有無を判定したか
- [ ] I/O を独立段落で一望できる形にしたか
- [ ] before→after で「値の意味が変わるか」を切り分けたか
- [ ] 既存テストと本変更で追加されたテストを分けて列挙したか
- [ ] 各テストが変更した分岐・条件を実際に通しているか確認したか
- [ ] 非自明なドメイン語を、コード上の実体とセットで解説したか
- [ ] 図の記法を出力先に合わせたか
- [ ] 推測を断定として書いていないか

## 出力フォーマット

### `impact` モード（既定）

```markdown
## review-io-impact 結果

> モード: impact ／ プロジェクト map: 使用（`.claude/review-io-impact/io-surface-map.md`） / 未使用（汎用シグナル）

### 📋 変更サマリ
- **変更対象**: どのファイル/クラス/関数を、どう変えたか（層とあわせて簡潔に）

### 🔀 input→output 影響マップ
（経路ごとに）
- **input**: 〇〇エンドポイント / △△ジョブ（入力の形）
  → **[変更箇所]**（層・関数）
  → **output**: 永続化 ×× テーブル / 出力ファイル / レスポンス・イベントのフィールド
- **影響条件**: この変更が output を変えるのはどういう条件か（1〜2行）

### 🗃 output 一覧
| 種別 | 出口 | 変更の影響 |
|---|---|---|
| 永続化 | テーブル/カラム | 変わる/変わらない・内容 |
| ファイル/CSV | 出力物・箇所 | … |
| レスポンス/イベント | フィールド | … |

### 🧪 テストカバレッジ
| 変更対象 | 単体（パス） | シナリオ/e2e（パス） | 方針上の要否 | 判定 |
|---|---|---|---|---|
| 〇〇 | あり: … / なし | あり: … / なし | 単体 / シナリオ / 両方 | ✅充足 / ⚠️不足 |

### ⚠️ カバレッジギャップと推奨
- **欠落**: 何の経路が、どのテスト種別で守られていないか
- **推奨**: 追加すべきテストの種別と配置先（＋方針上の根拠）
```

指摘（ギャップ）が無い場合は「📋 変更サマリ」「🔀 影響マップ」を示したうえで、「テストカバレッジは充足しています（追加提案なし）」と述べる。

### `explain` / `explore` モード

```markdown
## review-io-impact 結果（explain）

> モード: explain ／ プロジェクト map: 使用 or 未使用

### 📋 変更サマリ         … 何をどう変えたか（層つき）
### 🔄 I/O                … 入力/出力（リクエスト/レスポンス/永続化）
### 🚪 入口カタログ       … プロトコル別の表 ＋「影響しない入口」
### 🎯 合流点             … 収束点の明示（無ければ分岐のまま列挙）
### 🔁 before → after     … シグネチャ変化＋意味変化（explore では省略）
### ⛓ 因果連鎖           … 矢印1本の連鎖
### 🗃 出口               … output 一覧
### 🧪 テスト             … 既存/新規の単体・シナリオ/e2e と、変更経路の通過有無
### 📖 ドメイン・コード    … ドメイン語 ＋ コード上の実体
### 🗺 図                 … 全体図／入口別／出口
### ✅ 確認ポイント       … レビュアーが自分で判断すべき論点（断定しない）
```

#### 🔄 I/O 段落（独立段落として必ず置く）

処理全体の入口と出口を、経路を辿る前に**一望できる形**で先に示す。細部は後続の 🚪 入口カタログ・🗃 出口に譲り、ここでは「何を受け取り、何が残るのか」だけを対にして書く。

| | 内容 |
|---|---|
| 入力 | リクエスト/引数のフィールド、その値がどこから来るか（DB 由来か・呼び出し元が組み立てるか） |
| 出力 | レスポンスのフィールド、永続化されるテーブル/カラム、生成ファイル、発行イベント |

変更によって入力・出力の**形（型・必須性）**が変わったのか、**値の意味**だけが変わったのかを区別して書く。

#### 🧪 テスト段落

| 変更対象 | 既存テスト | 本変更で追加されたテスト | 変更経路を通るか | 判定 |
|---|---|---|---|---|
| 〇〇 | 単体: … / シナリオ・e2e: … | 単体: … / シナリオ・e2e: … | ✅通る / ⚠️通らない | ✅充足 / ⚠️不足 |

- **既存テストと新規テストを必ず分けて書く**
- 各テストが Step 7〜9 で洗い出した**分岐・条件を実際に通しているか**まで確認する（存在の有無だけで判定しない）
- シナリオ/e2e はプロジェクトのテストランナー名（runn 等）ではなく**役割**で分類する。ランナー名はパスと併記する程度に留める
- `explore` モードでは「本変更で追加されたテスト」列を省き、既存テストの所在のみ示す
