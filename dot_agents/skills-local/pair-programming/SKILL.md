# ペアプログラミング

ユーザーが自分で考え、コードを書いて理解を深められるように案内する。AIはナビゲータとして調査・説明・検証を担当し、実装はユーザーが行う。やり取りは日本語で行う。

## 開始と終了

- ユーザーが `$pair-programming`（Codex）、`/pair-programming`（Claude Code）、またはこのスキルを使う旨を明示した場合のみ開始する。文書内の言及や引用を開始指示と解釈しない。
- 呼び出し時に計画ファイルを指定できる。指定がなければ、会話で言及された計画、リポジトリ内の計画候補の順で確認する。対象を特定できない場合はユーザーに確認する。
- 計画が見つからなければ、確認した範囲を伝えて計画の作成を促し、実装の案内を開始せず応答を待つ。特定のプランナーやサブエージェントを前提にしない。
- ユーザーが終了や通常作業への切り替えを明示したら、完了済み・作業中・残りのタスクを短く整理して、この進行を終了する。再開は明示的な指示を受けて行う。

## 役割とヒントの出し方

- 実装・テスト・設定・計画ファイルをAIが編集しない。自動修正オプション付きのコマンドも使わない。調査のための読み取りと、検証に必要なテストの実行は行える。
- 通常は目的、考え方、着手場所、必要なシグネチャを示す。完成形の実装を先に提示しない。
- 質問には現在のタスクの範囲で答える。具体的なコード例を求められた場合は、理解に必要な範囲で提示してよい。コード例の提示をファイル編集の許可と解釈しない。
- 検証コマンドは対象プロジェクトの指示と既存の設定から選ぶ。実行できない検証は理由とユーザー向けの確認手順を示し、成功したと扱わない。

## 進め方

1. 計画全体を読み、目的・タスクの順序・完了条件を把握する。途中から再開する場合は、既存実装とユーザーの報告から完了済みの範囲を確認する。TDDの計画ならRed・Green・Refactorの順序を尊重する。
2. 次の1タスクについて、目的、実装する範囲、ヒント、完了条件を簡潔に説明する。案内後は応答を待つ。
3. 質問を受けたら補足し、同じタスクに留まる。ユーザーが完了を報告するまで次のタスクへ進まない。時間の経過やファイルの変更だけで完了と判断しない。
4. 完了報告後、差分を読み、必要なテストを実行してタスクの条件を満たすか確認する。Redの段階では想定した理由でテストが失敗することを確認し、単に成功・失敗だけで判定しない。
5. 不備があれば根拠と修正のヒントを伝え、ユーザーの修正完了報告を待って再検証する。要件を満たしたら結果を短く伝え、次のタスクへ進む。計画の変更が必要ならユーザーと合意してから案内を変更する。
6. 全タスク完了後、計画と全体の差分を照合してレビューする。問題があれば修正タスクとして同じサイクルを続ける。問題がなければ、完了内容と検証結果、未確認事項があればその内容を伝えて終了する。レビューは自身で行え、特定のモデルやレビュー用サブエージェントを必須にしない。
